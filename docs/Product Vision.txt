# MAGI

## Comprehensive Product Vision, Functional Specification & Design Philosophy

### Working tagline

**A personal instrument for thinking.**

### Design motto

**Made for the long future.**

### Foundational principle

> **The models will change. Your environment should not have to.**

---

# 1. The Vision

**Magi** is a persistent, personal AI environment designed to become an enduring workspace for thinking, creating, researching, remembering, and collaborating with artificial intelligence.

Magi is not simply a chatbot.

It is not primarily a wrapper around one particular AI model.

It is an environment in which:

* conversations persist
* Projects develop over time
* knowledge accumulates
* memory can be deliberately retained
* past conversations remain searchable
* Projects can selectively draw upon one another
* multiple AI models can collaborate and deliberate
* specialized tools can be invoked by AI or by the user
* reusable Skills can orchestrate tools and models
* specialized Agents can pursue tasks
* Councils can coordinate multiple intelligences
* documents and research become persistent resources
* images, characters, and visual styles can be maintained over time
* AI-generated artifacts can evolve through versions
* the user remains in control of accumulated context
* the underlying AI models can be replaced without destroying the user's environment

The fundamental premise is:

> **The user's relationship with AI should persist independently of any particular conversation, application, model, or provider.**

Magi therefore places the **user's accumulated context** at the centre of the experience rather than placing any particular AI model at the centre.

Models are instruments.

Magi is the environment in which those instruments are used.

---

# 2. The Problem Magi Solves

AI is changing extraordinarily quickly.

Models that were considered exceptional two years ago can already be obsolete or dramatically surpassed. New providers appear. Existing providers change their interfaces, pricing, capabilities, and policies. Specialized models emerge for reasoning, coding, image generation, research, audio, video, and other tasks.

This creates a fundamental problem.

A user's intellectual relationship with AI can become fragmented across:

* ChatGPT
* Claude
* Gemini
* coding environments
* image-generation applications
* research tools
* note-taking applications
* cloud drives
* local files
* browser sessions
* custom scripts
* increasingly specialized AI agents

Each system develops its own context.

None necessarily constitutes **the user's AI environment**.

Magi should occupy that missing layer.

The user should be able to change models without having to change *where their intellectual life with AI lives*.

Magi should sit conceptually **above the model layer**.

```text

          └────────────────┼────────────────┘
```

* Skills

* preferences
* workflows

This is one of the central reasons for building Magi.

# 4. Why "Magi"

The name **Magi** has several layers of meaning.

It evokes the **Magi of Evangelion**: multiple artificial intelligences whose distinct perspectives contribute to a larger decision-making system.

It also evokes the **biblical Magi**: seekers of knowledge who travel toward something significant, bringing different gifts and perspectives.

Most importantly, the name suggests that intelligence need not be singular.

Magi can contain:

* one AI
* several AIs
* competing AIs
* specialized AIs
* human judgment
* accumulated human knowledge

The system's intelligence emerges from the **relationship between them**.

The Evangelion reference should remain subtle. Magi should not visually imitate Evangelion.

The deeper idea is:

> **Multiple intelligences, brought together in pursuit of understanding.**

# 5. The Product Philosophy

Magi should be guided by seven principles.

## 5.1 Context belongs to the user

The user's accumulated knowledge, Projects, conversations, and creative work should not conceptually belong to any particular AI model.

Models may change.

Providers may change.

Interfaces may change.

The user's intellectual environment persists.

---

## 5.2 A conversation is an episode, not a home

Conversations are valuable records of thought, but they are not the fundamental organizational unit.

A conversation belongs to a larger Project.

A Project belongs to the larger personal environment.

---

## 5.3 Memory should be deliberate

Something said once should not automatically become permanent knowledge.

Magi should distinguish between:

* conversation history
* retrieved context
* Project knowledge
* Project memory
* global memory
* established facts
* AI suggestions

---

## 5.4 Boundaries matter

Projects should remain meaningfully separate.

Cross-project knowledge should be possible, but controlled.

Magi should never silently blur boundaries.

---

## 5.5 Intelligence can be plural

A single model is not always the best way to approach a difficult problem.

Magi should support:

* independent analysis
* debate
* critique
* revision
* red-teaming
* expert panels
* synthesis

---

## 5.6 Tools should belong to the environment

Models should not be the user's only interface to capabilities.

Magi should provide a stable tool layer that models can use.

A model can change while the capability remains.

---

## 5.7 The interface should endure

Magi should not chase visual fashions.

It should feel like technology designed to remain useful for decades.

> **Not futuristic-looking technology.
> Technology designed for the future.**

---

# 6. The Aesthetic: Instrumental Futurism

Magi's visual language can be described as:

## **Instrumental Futurism**

It imagines a future in which technology has matured.

The future no longer needs to announce itself with neon, gradients, holograms, or spectacle.

Technology is simply there.

Precise.

Powerful.

Quiet.

Durable.

The aesthetic draws inspiration from:

* Braun industrial design
* the Ulm School
* mid-century modernism
* scientific instruments
* observatories
* libraries
* early computing
* technical drawing
* architectural drafting
* Japanese information design
* restrained retrofuturism
* excellent editorial typography

The references should influence **principles rather than decoration**.

---

# 7. What Magi Should Not Look Like

Magi should reject the generic visual language of contemporary AI products.

Avoid:

* purple AI gradients
* glowing neural networks
* excessive glassmorphism
* floating translucent cards
* neon accents
* cyber effects
* decorative particles
* fake holograms
* robot imagery
* excessive rounded corners
* pill-shaped interfaces everywhere
* giant empty-state illustrations
* excessive emoji
* startup visual clichés

It should not look like:

> "another AI app."

It should also not become retro cosplay.

No fake CRT scanlines.

No fake rivets.

No fake mechanical switches.

No decorative pseudo-industrial details.

The goal is not to recreate 1965.

It is:

> **Imagine what serious designers of an earlier technological age would have created if they possessed today's capabilities.**

# 34. Permissions

Tools should operate through explicit permissions.

A model should not automatically inherit unlimited access to everything available to Magi.

The user should be able to specify:

```text

Read Project Files  ✓
```

* global
* Project
* Skill
* Agent
* individual operation

Potentially dangerous actions should require confirmation.

# 35. Skills

Skills are **reusable methods for accomplishing classes of tasks**.

A Skill is more than a tool.

A tool says:

> "Search the web."

A Skill says:

> "Conduct a rigorous research investigation."

A Skill may combine:

* instructions
* tools
* models
* Project context
* decision rules
* output formats
* validation
* iterative processes

---

# 37. Skills as Persistent Objects

> **Historical Research**

* Magi globally
* the user

---

# 38. Agents

Agents are more autonomous than Skills.

A Skill describes **how to do something**.

An Agent is an actor capable of **pursuing an objective using Skills, models, and tools**.

For example:

> "Investigate whether this historical claim is defensible and produce a report."

An Agent might:

1. formulate research questions
2. search
3. read documents
4. compare evidence
5. ask another model to critique the findings
6. revise
7. produce a report
8. save the result as a Project artifact

Agents should operate within explicit boundaries.

---

# 39. Skills, Agents, Models and Tools

The conceptual hierarchy becomes:

```text
TOOL
A capability.

SKILL
A reusable method.

MODEL
A source of intelligence.

AGENT
An actor pursuing an objective.

COUNCIL
Multiple intelligences/agents working together.

MAGI
The environment coordinating everything.
```

This hierarchy should inform the architecture without forcing the user to understand it.

# 42. Council Modes

Magi should support:

### Independent Analysis

Several models answer independently.

### Debate

Models argue opposing positions.

### Critique

One model evaluates another.

### Revision

### Red Team

A model attacks the argument.

### Expert Panel

Models assume different expert roles.

### Iterative Refinement

Draft → critique → revision → critique → final.

### Synthesis

Several analyses are reconciled.

# 44. Preserving Disagreement

Magi should not automatically collapse disagreement.

If three models disagree:

> **Consensus: Moderate**

> Two models support A.
> One supports B.

> **Key disagreement:**
> The conclusions depend primarily on different interpretations of X.

The user should be able to inspect the underlying arguments.

* email
* code
* external services

security must be fundamental.

The user should understand:

* what a model can access
* what a Skill can access
* what an Agent can access
* what a Council can access
* what external services are connected
* what actions require confirmation

Power should always be accompanied by control.

---

# 67. The Visual Language

Magi's interface should rely heavily on:

* typography
* spacing
* alignment
* restrained borders
* subtle surfaces
* carefully controlled hierarchy

rather than:

* gradients
* excessive shadows
* decorative cards
* visual noise

The interface should feel like **one instrument**.

---

# 68. Typography

Typography should communicate:

> **library + laboratory**

rather than:

> startup + social network.

The system should use:

* highly legible interface typography
* restrained display typography
* readable long-form text
* technical/monospaced typography where appropriate

Typography should carry much of the brand.

---

# 69. Colour

The foundation should be restrained:

* warm off-white
* paper
* charcoal
* graphite
* warm black
* muted grey

One controlled accent colour can establish identity.

Potential directions:

* oxidized orange
* vermilion
* deep ochre
* dark teal
* muted blue
* warm amber

The accent indicates **action or state**, not decoration.

---

# 70. Light and Dark Modes

Both should exist.

### Light

Paper + graphite + instrument.

### Dark

Dark laboratory + warm instrumentation.

Dark mode should avoid pure black and remain comfortable for long sessions.

---

# 71. Physicality Without Skeuomorphism

Magi should possess subtle physical qualities through:

* precise borders
* small surface differences
* restrained shadows
* tactile controls
* deliberate spacing
* strong alignment

A control should feel like a control.

A document should feel like an object.

A Project should feel like a place.

A Council should feel like a group being convened.

But none should become theatrical.

---

# 72. Motion

Animation should communicate:

* transition
* causality
* hierarchy
* state

It should not communicate:

> "Look how futuristic we are."

Council stages might subtly move through:

**Question → Analysis → Critique → Synthesis**

Motion should explain rather than decorate.

---

# 73. Icons

Icons should be:

* simple
* geometric
* restrained
* consistent

Typography should carry more of the interface than icons.

---

# 74. The Magi Mark

The logo should be simple enough to work:

* at 16px

# 77. Representative User Story: Research

A user asks:

> "Is this historical claim actually defensible?"

Magi recognizes that this is a substantial research question.

The user says:

> "Use the Historical Research Skill."

Magi invokes the Skill.

The Skill uses appropriate tools.

Several models investigate independently.

A Council compares their findings.

A skeptic attacks the emerging conclusion.

A synthesizer produces a report.

The user approves the report.

Magi saves it as a Project artifact and optionally promotes key conclusions into Project knowledge.

The original conversation remains in the archive.

The research remains available for future work.

---

# 78. Representative User Story: Creative Work

A user enters an Image Project.

They say:

> "Create a new illustration of Mira."

Magi knows:

* the character
* the Style Guide
* canonical references
* relevant Project context

The user generates several variations.

One becomes the preferred reference.

Magi records it.

Later:

> "Put Mira into the new scene we're developing."

The character and visual language persist.

---

# 79. Representative User Story: Cross-Project Thinking

The user is working on a new educational Project.

They ask:

> "Have I thought about this before?"

Magi searches the archive.

It finds discussions in several Projects.

It presents the relevant material and provenance.

The user says:

> "Bring the useful parts into this Project, but don't merge the Projects."

Magi retrieves and contextualizes the information.

The Projects remain distinct.

---

# 80. Representative User Story: Council

The user encounters a difficult philosophical question.

They say:

> "Magi Council. Three independent analyses. Then have them critique one another. I want the final synthesis, but show me the major disagreement."

Magi:

1. selects appropriate models
2. runs independent analyses
3. circulates their conclusions
4. conducts critique
5. identifies disagreements
6. synthesizes
7. presents the final answer
8. preserves the Council record

The user can later return to the deliberation.

---

# 81. Representative User Story: Model Replacement

A user has worked on a Project for two years.

Their preferred model becomes obsolete.

They switch to a new model.

The Project does not need to be recreated.

The new model receives the relevant:

* Project context
* memory
* documents
* artifacts
* instructions
* Skills
* tools

The user continues working.

This is the central durability promise.

---

# 82. Representative User Story: External Tools

The user says:

> "Analyze this dataset."

Magi selects an appropriate analysis Skill.

The Skill invokes a computational tool.

The tool produces results.

The model interprets them.

The resulting analysis becomes an artifact.

The user never needs to care which underlying tool executed the computation unless they want to inspect it.

---

# 83. Representative User Story: Agent

The user says:

> "Investigate this question and prepare a report by tomorrow."

Magi creates an Agent task within appropriate boundaries.

The Agent can:

* research
* read
* analyze
* consult models
* use Skills
* produce an artifact

The user can inspect its progress and intervene.

The Agent cannot exceed its permissions.

The ultimate goal is not merely to create another application.

Like a personal library.

Like a workshop.

Like a studio.

Like a laboratory.

The user may change tools within it.

# 87. What Magi Should Not Become

Magi should not become:

* a social network
* an AI marketplace first and foremost
* a collection of disconnected AI gimmicks
* a replacement for every specialist application
* an opaque autonomous system
* a model-specific product
* a dashboard overloaded with capabilities
* a system that silently decides what the user believes or remembers

Its purpose is narrower and deeper:

> **Give one person a durable environment in which artificial intelligence can be used intelligently.**

# 88. The Long-Term Possibility

If built correctly, Magi could become an interface between the user and an increasingly diverse AI ecosystem.

Today's models might be:

* GPT
* Claude
* Gemini
* specialized reasoning models
* image models
* coding models
* local models

Tomorrow's models may be entirely different.

Magi does not need to predict which will win.

It needs to make their changing capabilities **available within a stable environment**.

The user should be able to say:

> "Use the best tool for this."

without having to rebuild their entire workflow every time the AI industry changes.

---

# 89. The Deeper Product Idea

Magi changes the unit of AI interaction.

The dominant paradigm is:

> **Prompt → Response**

Magi's paradigm is:

> **Person → Environment → Context → Intelligence → Tools → Creation → Memory**

The user's accumulated knowledge becomes part of the interface.

The Project becomes part of the intelligence.

The archive becomes searchable.

Different models become collaborators rather than competitors.

Tools become instruments.

Skills become reusable methods.

Agents become delegated actors.

Councils become collective intelligence.

Images become persistent creative assets.

AI outputs become artifacts rather than disposable messages.

The system grows with the user.

# 93. The Design Question

The most important design question is not:

> "What will make this interface look futuristic?"

It is:

> **"What will still feel right in 2045?"**

That question should govern both the software architecture and the visual design.

The architecture should survive changing models.

The data should survive changing providers.

The interface should survive changing fashions.

The Projects should survive changing workflows.

The user's knowledge should survive changing applications.

---

# 94. The Ultimate Promise

Magi is not trying to predict which AI will be best.

It is trying to ensure that **the user remains in a position to benefit from whichever AI is best.**

The models are temporary.

The providers are temporary.

The interfaces are temporary.

The user's accumulated intellectual environment is the thing worth preserving.

Magi is therefore ultimately a project about **continuity in a rapidly changing technological landscape**.
